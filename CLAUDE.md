@AGENTS.md

## Project overview

Micro-MCP (미니 업무 비서 / "나만의 AI 업무 비서") is a Next.js 16 (App Router) PWA. Users toggle "MCP blocks" (web search, document analysis, deadline tracking, writing assistant, meeting-notes structuring) and issue prompts against an AI backend that assembles context from those blocks. All UI copy and AI-facing prompts are in Korean.

## Commands

- `npm run dev` — start dev server (localhost:3000)
- `npm run build` — production build
- `npm run start` — run production build
- `npm run lint` — ESLint (flat config via `eslint.config.mjs`, extends `eslint-config-next` core-web-vitals + typescript)

There is no test suite configured in this repo.

## Architecture

### Single-page client app + thin API routes

Almost all UI and state lives in one client component, [app/page.tsx](app/page.tsx) — tabs (workspace / deadlines / MCP blocks / monitoring / logs) are rendered conditionally from `activeTab` state rather than via routing. "MCP blocks" are just booleans (`isSearchActive`, `isFileActive`, `isDeadlineActive`, `isWritingActive`, `isMeetingNotesActive`) sent to the API, not a real plugin/tool-calling protocol. Block toggle state, uploaded files, and deadlines persist to `localStorage` (not the DB) and are re-sent with every prompt.

The actual AI work happens server-side in a few routes:
- [app/api/chat/route.ts](app/api/chat/route.ts) — main chat endpoint. Builds a single system prompt by concatenating: recent Supabase `logs` rows, the user's deadline list, every "교수님" tab document (grouped and labeled by professor name + school/department, queried server-side via the request's Supabase token — RLS already scopes it to the caller, so nothing is sent from the client for this), parsed file contents, and (if search is active) live Tavily search results — then streams an OpenAI (`gpt-4.1-mini`) chat completion back as a raw text stream (`export const dynamic = 'force-dynamic'` so it isn't buffered). [app/page.tsx](app/page.tsx) still contains client-side parsing for a `<!--ACTION_ITEMS_JSON-->...<!--END_ACTION_ITEMS_JSON-->` sentinel block (`handleAddDetectedDeadline`/`detectedActionItems`) from an earlier "meeting notes" block design — this route no longer instructs the model to emit that sentinel, so that parsing path is currently dead code, not a bug to chase if action items never appear.
- [app/api/analyze/route.ts](app/api/analyze/route.ts) — takes `{text, fileName?, lens?}`, picks a lens from [lib/lenses.ts](lib/lenses.ts) (`deadlines`/`questions`/`digest`, auto-detected via `detectLens()` when `lens` is omitted), and calls OpenAI with Structured Outputs (`response_format: json_schema`, `strict: true`) to force the lens's JSON shape. Drives the "MCP 블록 매니저" (circuit) tab: uploading a document there calls `/api/extract` for text, `detectLens()` to pick a lens, then this route for the result.
- [app/api/extract/route.ts](app/api/extract/route.ts) — takes an uploaded file (base64) and returns plain text, via the shared [lib/file-text-extract.ts](lib/file-text-extract.ts) (PDF via `unpdf`, `.docx` via `mammoth`, `.xlsx/.xls/.csv` via `xlsx`, `.pptx`/`.hwpx` via `jszip` + manual XML tag-stripping, `.hwp` via `cfb` (CFBF container) + `pako` (raw-deflate `BodyText/SectionN` streams) + a hand-rolled walk over `HWPTAG_PARA_TEXT` records — encrypted `.hwp` files and pre-5.0 (non-CFBF) versions get distinct Korean guidance messages instead of a generic failure). This is the one file-reading implementation shared across routes that need plain extracted text — don't reintroduce a second copy of it. Deliberately doesn't reuse `@ohah/hwpjs` (used by `/api/chat` below) for `.hwp`: that library's public API doesn't document a reliable way to distinguish encrypted vs. too-old-to-parse vs. generic-corruption failures, which this route needs for its per-case messaging.
- [app/api/analyze-professor/route.ts](app/api/analyze-professor/route.ts) — takes either `{ documents: {fileName, text, docType}[], professor?: {school, department} }` (full mode — already-extracted text, one entry per file; `docType` is one of `lecture`/`exam`/`assignment`/`paper`) or `{ previousResult, newDocuments: {fileName, text, docType}[], professor? }` (incremental mode — `previousResult` is the professor's existing 6-category result, `newDocuments` only the just-added files), tags each document with its type in the combined prompt text, and calls OpenAI with a fixed Structured Outputs schema. The schema has 6 categories (`topics`/`examStyle`/`assignmentStyle`/`examQuestionTypes`/`gradingStrictness`/`researchInterests`), each shaped `{confident: boolean, items: string[]}` — the model only sets `confident: true` (and fills `items`) when a pattern is corroborated across multiple documents, so with too little material a category comes back `confident: false, items: []` rather than fabricating a pattern from one data point. `researchInterests` is instructed to draw only from documents tagged `paper` — if none of the uploaded documents are papers it stays `confident: false`. When `professor.school`/`department` are given, a line is appended to the system prompt ("이 교수님은 OO 소속입니다...") so the model interprets major-specific terminology and grading conventions correctly.

  Full mode uses `BASE_SYSTEM_PROMPT`; incremental mode uses a separate `INCREMENTAL_SYSTEM_PROMPT` that instructs the model to update (not regenerate from scratch) each category based on whether the new documents corroborate, contradict, or are irrelevant to what's already there — both share a `CATEGORY_INSTRUCTIONS` constant for the 6-category descriptions so they can't drift apart. A per-call cap (`MAX_PROFESSOR_DOCUMENTS = 30`, mirrored client-side in `app/page.tsx`) rejects `documents`/`newDocuments` arrays larger than that.

  Drives the "교수님" tab: documents are uploaded per-professor via `/api/extract` and persisted (with their extracted text and `doc_type`) in the `documents` table so re-analysis never needs the files re-uploaded. `app/page.tsx` no longer has one `recomputeProfessorAnalysis()` — it's split into `recomputeProfessorAnalysisIncremental()` (called after every successful upload; sends only the new documents plus the existing `professor_analysis.result`, which is far cheaper than re-sending everything as the document count grows) and `recomputeProfessorAnalysisFull()` (called after every deletion, and by the manual "이 교수님 분석" button / circuit board node click; re-sends every remaining document, since removing a document isn't something an incremental prompt can safely undo — the model has no way to tell which existing conclusion came from the now-deleted file). Both funnel through a shared `runProfessorAnalysis()` helper that does the actual fetch + `professor_analysis` upsert, retries once automatically on failure, and — if the retry also fails — sets `professorAnalysisError` (shown inline on the professor detail screen) **and** fires an `alert()` (because the upload that triggered the failure may have happened from the professors *list* screen's "자료 올리기" panel, which doesn't render that inline error). Before doing an incremental update, `recomputeProfessorAnalysisIncremental()` cross-checks `professor_analysis.document_count` against the actual document count excluding the just-added files; a mismatch (residue from an earlier failed update) makes it fall back to `recomputeProfessorAnalysisFull()` automatically instead of compounding drift on top of a stale summary — this self-heals on the next upload without requiring the user to notice the alert and manually click "이 교수님 분석" first. (To zero remaining documents after a deletion, the `professor_analysis` row is deleted instead of recomputed.) Client-side UI splits categories by `confident` into shown-now vs. a grayed-out "더 올리면 알 수 있는 것" teaser that a category moves out of once it flips to `confident: true`. Registering a professor requires school+department (client-side validation only, not a DB constraint); [app/page.tsx](app/page.tsx) remembers the last-entered school/department per user (`loadUserScopedItem`/`saveUserScopedItem`, key `mcp_professor_defaults`) and prefills them (still editable) the next time the "새 교수님 등록" form opens. Both system prompts use the same prose-not-bullets structure as `lib/lenses.ts`'s `COMMON_RULES` below, for the same reason.

File parsing in `/api/chat` is dispatched by extension: `.xlsx/.xls/.csv` → `xlsx`, `.hwp/.hwpx` → `@ohah/hwpjs`, `.pptx/.docx/.pdf` → `officeparser`, images → `tesseract.js` OCR (`eng`+`kor`). Legacy `.ppt`/`.doc` binary formats are explicitly rejected with a message asking users to re-save as `.pptx`/`.docx`. Both this route and `/api/extract` (via `lib/file-text-extract.ts`) determine "extension" through the shared `resolveFileExtension(fileName, mimeType)` rather than a raw `fileName.endsWith(...)` check: some mobile share-sheet/cloud-picker flows hand the browser a `File` with a generic or missing name (no `.pptx` etc.) but a correct MIME type, and a pure-extension check silently rejected those as "unsupported format." `resolveFileExtension` falls back to a small MIME→extension table when the filename's extension is missing or unrecognized. Keep using this helper for any new file-type dispatch — don't reintroduce a bare `.endsWith()` check.

Images attached directly in chat (`chatAttachments`, kind `image`) skip OCR entirely — they're sent to `gpt-4.1-mini` as base64 `image_url` content parts, no separate tool. `app/page.tsx`'s `resizeImageDataUrl()` downscales anything wider than 1568px on its long edge (via an off-DOM `<canvas>`, re-encoded as JPEG) before attaching, purely to cut the base64 payload/token cost for phone-camera photos — images already at or under that size are left in their original format untouched (so ordinary screenshots keep PNG transparency). The system prompt tells the model to read multiple attached images as one continuous document/conversation in upload order (e.g. a chat log split across several screenshots) and to say so explicitly rather than guess when part of an image is unreadable. `SUPPORTED_CHAT_IMAGE_MIME_TYPES` allowlists only what OpenAI vision actually accepts (png/jpeg/gif/webp) and rejects anything else (notably HEIC/HEIF, the default iPhone photo format) at attach time with an actionable Korean message, instead of silently sending an undecodable image through.

Web search (Tavily) is the one context source that isn't always-on: `useWebSearch` defaults to `false` and is only `true` when the user taps the "웹 검색 ON/OFF" toggle next to the chat input (state: `isSearchActive` in `app/page.tsx`) — it's the one opt-in because it's slower and costs extra per call. `/api/chat` logs the query it sends Tavily and the result count (`[웹 검색] ...`), and — unlike the original implementation — checks `res.ok` before parsing the Tavily response; previously a non-2xx Tavily response (bad/expired key, rate limit) parsed as `{results: undefined}` and silently fell through to "no results found," which looked identical to a normal empty search and left no error in the logs. If web search seems to be silently failing, check Vercel logs for `[웹 검색]` lines and a non-2xx status before assuming the prompt is wrong. The Vercel `TAVILY_API_KEY` is marked Sensitive, so `vercel env pull` returns a `[SENSITIVE]` placeholder instead of the real value — it can't be retrieved through the CLI for local testing; verifying a live Tavily call has to happen by testing through the deployed app and checking logs afterward, not by scripting against the real key locally.

`/api/chat`'s system prompt explicitly states today's date (computed server-side with `timeZone: 'Asia/Seoul'`, since Vercel functions default to UTC and the model has no other way to know "today" past its training cutoff) — without this line the model would guess or fall back to training-cutoff-era dates when asked anything date-relative ("이번 주", "며칠 남았어"), which is what caused reports of "오늘 날짜가 제멋대로."

Both AI-facing prompts explicitly instruct the model to treat file/search/log content as untrusted data and ignore any embedded instructions — preserve this prompt-injection guard when editing either system prompt.

**AI response language** is a separate concept from the UI's ko/en `locale` (which still only drives next-intl's menu/button translations via `useLocale()`/`LocaleSwitcher` and is untouched by any of this). `app/page.tsx` tracks its own `responseLanguage` string state (e.g. `"Korean"`, `"Japanese"`, `"Spanish"` — a human-readable English language name, not a locale code), auto-detected on first load from `navigator.language` via `detectBrowserLanguageName()` (uses `Intl.DisplayNames(['en'], {type:'language'})`, so it isn't limited to `SUPPORTED_LOCALES`'s ko/en — any language the browser reports gets a real name), then persisted per-account (`loadUserScopedItem`/`saveUserScopedItem`, key `mcp_response_language`) once the user overrides it via the "AI 답변 언어" `<select>` in the sidebar (`COMMON_RESPONSE_LANGUAGES` seeds the option list, but the current value — even an unlisted auto-detected one — is always included so it never silently reverts). This value is sent as `responseLanguage` on every `/api/chat`, `/api/analyze`, and `/api/analyze-professor` call, and each route (or the shared `runLensAnalysis()` in `lib/run-lens-analysis.ts`, used by the first two) prepends the exact same instruction — `"Respond entirely in {responseLanguage}. This overrides the document's language."` — **to the user-role message content, never to the system prompt** (`lensDef.systemPrompt`/`BASE_SYSTEM_PROMPT`/`INCREMENTAL_SYSTEM_PROMPT` for the lens routes; `/api/chat`'s `systemInstruction` is already unique per request — it embeds the current KST date and per-user context — so it was never a stable cache prefix to begin with, but the directive still goes in the user message there too, for consistency with the other two routes and because that's where the analogous placement already lived). For the two lens routes this preserves OpenAI's automatic prompt-caching on `COMMON_RULES`/`CATEGORY_INSTRUCTIONS` exactly like the `locale` mechanism this replaced did — see the note on `COMMON_RULES` below for why that matters. `lib/lenses.ts`'s `COMMON_RULES` and `analyze-professor`'s `CATEGORY_INSTRUCTIONS` both end with "사용자가 지정한 언어를 따르세요" (follow the user-specified language) rather than the old "문서가 한국어로 작성되어 있다면 한국어로" (Korean if the document is Korean) — the old wording actively fought the new per-request directive when a non-Korean `responseLanguage` was requested on a Korean document. `/api/public-analyze` (the anonymous trial route) does **not** pass `responseLanguage` to `runLensAnalysis()` — it has no user preference to read, so it falls through to no directive (same as the pre-this-feature default). Every error string `/api/chat`, `/api/analyze`, and `/api/analyze-professor` return to the client is in English now (rate-limit/size-limit/parse-failure/catch-all messages) — deliberately narrower than a full app-wide English pass: fixed UI chrome (menus, buttons, the rest of `app/page.tsx`'s alerts) stays Korean-first as before, only the error surface of these three AI-response routes changed, since those are the ones a now-non-Korean-speaking user is most likely to actually hit.

The "마감 뽑기" lens's `date` field is deliberately the source document's date phrase verbatim (`lib/lenses.ts` tells the model not to compute or normalize relative/partial dates), which is very often a bare Korean or ICS-style format (`"3월 15일"`, `"5/21"`, `"20260315T090000Z"`) that plain `new Date(raw)` either fails to parse (→ silently falls back to "today", which is how every registered deadline once ended up showing D-DAY) or mis-parses (`new Date("3/15")` silently lands in year 2001). `app/page.tsx`'s `tryParseDeadlineDate()` handles this with explicit regexes for those formats — checked in this order — before ever falling through to the native parser; year-less dates infer next year when the current-year candidate has already passed. Don't replace this with a bare `new Date(raw)` call again.

[lib/lenses.ts](lib/lenses.ts)'s `COMMON_RULES` (shared anti-hallucination rules prepended to every lens's `systemPrompt`, requiring an evidence field — a verbatim source quote — on every array item, dropping items that can't cite one) is written as prose with an explicit "don't second-guess content that's actually there" framing rather than a flat bullet checklist. This isn't a style choice: an earlier bullet-list version of the same rules made `gpt-4.1-mini` collapse to refusing the entire `digest` lens (`summary: "자료에 없습니다"` with empty arrays) on ~20% of calls even when the source text plainly had content — stacking that many independent hedging rules as parallel bullets was enough to trigger self-censorship. The prose version fixed it (0/20 in testing). Don't reflatten this into a bullet list without re-running that kind of repeated-call test. The evidence field is named `evidence` on every lens except `questions`, whose `QuestionItem.source_quote` plays the identical role (never renamed the others — `evidence` isn't rendered anywhere for `questions` so the rename was risk-free, but there was no reason to touch the working lenses too). The `questions` systemPrompt additionally warns against presenting "최대 8개" as a hard target: an earlier version instructing "최대 8개의 질문을 뽑으세요" made the model pad out ungrounded questions with a fake `"자료에 없음"`-style `source_quote` to hit the count (measured 15/48 fabricated quotes across 6 runs) rather than returning fewer, properly-grounded questions — the fix was to explicitly say fewer-but-grounded beats hitting the count, plus name the anti-pattern (don't write "자료에 없음" into the quote field, just drop the question) (0/12 after the fix). Same lesson as the bullet-list issue above: test any prompt change with several repeated real calls, not one.

The "교수님" tab's detail view reuses [components/circuit/circuit-board.tsx](components/circuit/circuit-board.tsx) a second time (non-`compact`, so all 3 columns render) with a dedicated 5-node subgraph — `professor_docs` (source) → `professor_ai_core` (lens/"AI 코어" visual) → `expected_questions`/`assignment_direction`/`study_method` (action, the max the shared column-position math in `lib/circuit/geometry.ts` assumes per layer). These 5 ids were added to `NodeId` (`types/blocks.ts`) and `NODE_REGISTRY` (`lib/blocks/defaults.ts`) alongside — not replacing — the original 9 used by the chat mini-wire; the two graphs never mix nodes. Clicking the source or AI-core node calls `recomputeProfessorAnalysis()` (same function the "이 교수님 분석" button calls); the 3 action nodes don't trigger anything themselves — they're read-only, mapped from the already-computed 6-category `professor_analysis` result (`PROFESSOR_CIRCUIT_DEFS` in `app/page.tsx`: `expected_questions` ← `examStyle`+`examQuestionTypes`, `assignment_direction` ← `assignmentStyle`, `study_method` ← `topics`, chosen because "공부 방식" has no clean 1:1 category match). No new API calls are made for this view. The wire-lighting animation is `CircuitBoard`'s existing built-in one (retriggers because the graph object is freshly computed every render, matching the chat mini-wire's `chatLensGraph` pattern); the 3 result cards below it get their own separate staggered CSS reveal (`.professor-circuit-reveal`, 300ms apart, remounted via `key={analysisRow?.updated_at}`) since the underlying analysis is one API call, not 3 sequential ones — there's no real "one at a time" arrival to animate against.

### Auth

Supabase Auth (email/password + Google OAuth) gates the whole app via [middleware.ts](middleware.ts): any request that isn't in `isPublicRoute` (`/login`, `/auth/*`, `/privacy`, `/pricing`, `/api/cron/*`, `/api/public-analyze`) requires a session, redirecting to `/login` (or returning a 401 JSON for `/api/*`). Because middleware already enforces this, the API routes under `app/api/` do **not** re-check auth themselves (see the comment at the top of each route) — don't add redundant auth checks there, but also don't remove the middleware gate without adding auth to those routes. `/api/public-analyze` is the one route that deliberately allows anonymous callers and does its own (non-session) abuse check instead — see "Anonymous trial" below.

- [app/login/page.tsx](app/login/page.tsx) and [app/page.tsx](app/page.tsx) both construct their own `createBrowserClient` from `@supabase/ssr` using `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- [app/auth/callback/route.ts](app/auth/callback/route.ts) exchanges the OAuth `code` for a session server-side (`createServerClient`) and redirects to `/`.
- Signing up no longer strands the user on a "check your email" screen when it doesn't have to: `handleAuth`'s sign-up branch checks whether `supabase.auth.signUp()` returned a `data.session` — if it did (meaning the Supabase project's Authentication → Email → "Confirm email" setting is off), it logs the user straight into the app, same as a normal sign-in, while Supabase still sends the confirmation email in the background. If `data.session` is `null` (confirm-email is required), the app falls back to the original "we sent you a confirmation email" message, because that gate is enforced by Supabase itself at the project-settings level — **this is a Supabase Dashboard toggle, not something this codebase can turn off from code**. If instant post-signup access isn't actually happening in production, check that setting first before assuming the client code is wrong.

### Anonymous trial (no-login file analysis)

[app/login/page.tsx](app/login/page.tsx) has a second mode ("로그인 없이 파일 하나 체험해보기" / "Try it without an account", toggled by local `showTrial` state) that lets a visitor analyze one file — full lens result shown inline — without an account. This exists specifically so the first thing a new visitor does isn't a signup wall. Deliberately narrow scope: file analysis only, no chat, no web search, no professor/deadline features (those still require login exactly as before — the trial doesn't expose new surface area for them, it just adds this one path).

- [app/api/public-analyze/route.ts](app/api/public-analyze/route.ts) is the route behind it — allowed through `middleware.ts` without a session (see "Auth" above). Abuse control is completely different from every other route in this app because there's no user account to rate-limit: it keys off request IP (`x-forwarded-for`, falling back to `x-real-ip`, falling back to a shared `'unknown'` bucket if neither header is present) against the `anonymous_trial_usage` table (`ip_address`, `created_at`, RLS enabled with **zero** policies — nothing but the service-role key can touch it, since there's no `auth.uid()` to scope a policy to), capped at 1 request per IP per rolling 24h via `SUPABASE_SERVICE_ROLE_KEY`. The file-size cap is `MAX_ANONYMOUS_UPLOAD_BYTES` (3MB, in `lib/upload-limits.ts`) — well below the 10MB authenticated limit. The IP's daily usage is recorded *before* extraction/analysis runs (right after the size check passes), not after a successful result — otherwise someone could burn free retries forever by deliberately sending malformed files, since a failed extraction wouldn't count against them. Migration: [supabase/migrations/20260802_create_anonymous_trial_usage.sql](supabase/migrations/20260802_create_anonymous_trial_usage.sql).
- The actual lens-analysis call (text truncation, lens detection, the OpenAI Structured Outputs request, JSON parsing) is shared with the authenticated `/api/analyze` route via `runLensAnalysis()` in [lib/run-lens-analysis.ts](lib/run-lens-analysis.ts) — both routes do their own, very different, abuse checks beforehand and then call the same function, so the two paths can't silently drift apart on how a lens result actually gets produced.
- "결과를 저장하려면 로그인하세요" / "Log in to save this result": when the trial produces a result, the panel shows a "Log in and save" button instead of any interactive per-item actions (no register-this-deadline button, etc. — those still require being logged in and exist only in the main app). Clicking it writes `{ fileName, text, lens, result, savedAt }` to `localStorage` under `PENDING_TRIAL_RESULT_KEY` ([lib/pending-trial-result.ts](lib/pending-trial-result.ts) — shared type/key between the two pages so they can't drift) and switches the panel back to the login form. **Deliberately stores the already-extracted text, not the original file** — keeps the payload small and means nothing needs to be uploaded a second time. `app/page.tsx` has a `useEffect` gated on `user && isFilesLoaded` (must run after the "load files from localStorage" effect, or that effect would overwrite what this one adds) that reads and clears this key on first render after login, adds the file to the local "내 파일" list, calls `recordDocumentUpload`, and restores `lensId`/`lensResult`/`lensStage` so the exact same result the visitor already saw reappears immediately — it does **not** call `/api/analyze` again, since re-running the OpenAI call on text that already produced a result would just be wasted cost.

### Data model (Supabase)

Referenced tables (schema itself lives in Supabase, not in this repo): `logs` (`user_id`, `content`, `response`, `status`, `created_at` — chat history, also used for a simple 10-req/min rate limit in `/api/chat`), `profiles` (`id`, `username`, `is_pro` boolean default `false` — see "Paid tier prep" below), `prompts` (`user_id`, `slug`, `content`), `document_uploads` (`user_id`, `file_name`, `format`, `created_at` — append-only metadata log written client-side via `recordDocumentUpload()` in [app/page.tsx](app/page.tsx), which powers the cross-device "나의 기록" tab's document-count/format breakdown. `user_id` defaults to `auth.uid()` and RLS restricts rows to their owner. Migration: [supabase/migrations/20260724_create_document_uploads.sql](supabase/migrations/20260724_create_document_uploads.sql). `recordDocumentUpload()` must be called from every place a user successfully adds a file — it was originally wired only into the "내 파일" tab's two upload handlers, so files added later via chat attachments (`handleChatAttachmentFiles`) or the "교수님" tab (`handleUploadProfessorFiles`) never counted, undercounting "나의 기록"; both now call it too. If a future upload path is added, call it there as well or the count will silently drift again.).

Four more tables back the "교수님" tab (per-professor document collection, own-rows-only via RLS, no cross-user sharing):
- `professors` (`user_id`, `name`, `school`, `department`, `created_at`).
- `documents` (`user_id`, `professor_id` (nullable FK → `professors.id`, `on delete cascade`), `file_name`, `format`, `content`, `doc_type` (`lecture`/`exam`/`assignment`/`paper`, default `lecture`, check-constrained — see [supabase/migrations/20260729_add_doc_type_to_documents.sql](supabase/migrations/20260729_add_doc_type_to_documents.sql)), `created_at` — unlike `document_uploads`, this table stores the actual extracted text so `/api/analyze-professor` can re-run over everything a professor has accumulated without re-uploading). Migration: [supabase/migrations/20260727_create_professors_and_documents.sql](supabase/migrations/20260727_create_professors_and_documents.sql).
- `doc_chunks` (`user_id`, `document_id` FK → `documents.id` `on delete cascade`, `chunk_index`, `content`, `created_at`) — [app/page.tsx](app/page.tsx)'s `chunkText()` splits each document's text into ~1500-char pieces at upload time and stores them here. Nothing reads this table back yet (analysis still uses `documents.content` in full) — it exists so a future chunk-level search/embedding feature doesn't need a backfill, and so document deletion has somewhere consistent to cascade into.
- `professor_analysis` (`user_id`, `professor_id` **unique** FK → `professors.id` `on delete cascade`, `result` jsonb, `document_count`, `updated_at`) — one row per professor, upserted (`onConflict: 'professor_id'`) by the client via the shared `runProfessorAnalysis()` helper in `app/page.tsx`, which every document upload and deletion routes through. `document_count` is the snapshot the "자료 N개 기준" framing line in the UI is computed from, not a live `documents` count query — see below for how it's kept from drifting after a failure.

Migration for `doc_chunks`/`professor_analysis`: [supabase/migrations/20260728_create_doc_chunks_and_professor_analysis.sql](supabase/migrations/20260728_create_doc_chunks_and_professor_analysis.sql). Migration for `documents.doc_type`: [supabase/migrations/20260729_add_doc_type_to_documents.sql](supabase/migrations/20260729_add_doc_type_to_documents.sql).

`conversation_folders` (`user_id`, `name`, `created_at`, RLS, no row limit) backs the "지난 대화" tab's folder filter/organization feature. `logs.folder_id` (nullable FK → `conversation_folders.id`, `on delete set null`) is the actual classification column — `null` means "미분류." `logs` predates the `supabase/migrations/` folder (no tracked DDL for its base schema, RLS unknown at the time this was added), so [supabase/migrations/20260730_create_conversation_folders.sql](supabase/migrations/20260730_create_conversation_folders.sql) defensively adds an UPDATE policy for `logs` too (needed for the folder-move client call, `.from('logs').update({folder_id})`) — permissive Postgres RLS policies are OR'd, so this is harmless even if an equivalent one already existed under a different name.

None of the above migrations are auto-applied — the app only holds the anon/service-role keys, not schema-change credentials, so each one has to be run manually via the Supabase SQL Editor.

### Env vars

Required at runtime (not committed; see `.env.local` locally):
- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` — used client- and server-side
- `SUPABASE_SERVICE_ROLE_KEY` — server-only, used by two routes that both have a legitimate reason to act across users rather than on behalf of one authenticated caller: `/api/cron/cleanup-logs` (see "Paid tier prep" below, bypasses RLS to delete free-tier users' old `logs`) and `/api/public-analyze` (see "Anonymous trial" below, bypasses RLS to check/record IP-based usage in a table no session can own). A prior public-ish REST route (`/api/v1/[username]/[slug]`) that used it was deleted for having no client call sites and a real ownership-check gap; don't add a third use of this key without the same scrutiny — it should stay reserved for "this operation is inherently cross-user," not become a convenient escape hatch from RLS.
- `CRON_SECRET` — the only auth for `/api/cron/cleanup-logs`; Vercel automatically sends it as `Authorization: Bearer $CRON_SECRET` when invoking a configured cron (see [vercel.json](vercel.json)). Set it to a long random string in both `.env.local` and the Vercel project's env vars.
- `OPENAI_API_KEY` — required by `/api/chat`, `/api/analyze`, and `/api/analyze-professor` (model: `gpt-4.1-mini`); routes return a clean JSON error if missing rather than throwing
- `TAVILY_API_KEY` — optional; if unset, the search block degrades gracefully (tells the model to say so rather than guess)

### Loading text

[components/loading-text.tsx](components/loading-text.tsx)'s `<LoadingText />` picks a random line from [lib/loading-messages.ts](lib/loading-messages.ts) (30 fixed Korean strings, no AI call) and swaps to a new random one every 3s; the trailing dot cycles `.`/`..`/`...`/`.` every ~0.5s via a global CSS `@keyframes loadingDots` animation (defined inline in `app/page.tsx`'s `<style jsx global>` block, class `.loading-dots`). ### i18n (next-intl)

Locale is decided by a single `locale` cookie (`'ko'` default, `'en'` the only other option — [i18n/locales.ts](i18n/locales.ts) is the source of truth for `SUPPORTED_LOCALES`), not URL-based routing (no `[locale]` route segments): this app is one client component (`app/page.tsx`) with tab state instead of real routes, so adopting next-intl's routing middleware would mean merging it with the existing custom Supabase-auth `middleware.ts` — out of scope for the "scaffold first" pass this was built in. [app/layout.tsx](app/layout.tsx) is now `async`, reads the cookie server-side via `getLocale()`/`getMessages()` (from `next-intl/server`, configured in [i18n/request.ts](i18n/request.ts)), and wraps `children` in `NextIntlClientProvider` — this makes every route under it dynamically rendered (no more static prerender for `/` or `/login`), an accepted tradeoff since `/` was already effectively per-user/dynamic behind the auth gate. [components/locale-switcher.tsx](components/locale-switcher.tsx) is the toggle (writes the cookie, calls `router.refresh()`); it imports locale constants from `i18n/locales.ts`, **not** `i18n/request.ts` — that file pulls in `next/headers`, which breaks the client bundle if imported from a Client Component (hit this exact build failure once already; keep the split).

Coverage in [messages/ko.json](messages/ko.json)/[messages/en.json](messages/en.json) is being migrated incrementally, tab by tab (an explicit scope decision — scaffold the infra correctly first, migrate the rest later — not an oversight; don't assume every visible string across `app/page.tsx` is translated yet). Done so far: sidebar nav labels, the chat send button, the initial session-loading screen, and — as of the most recent pass — the full "물어보기" (workspace/chat) tab under the `workspace` namespace: the idle greeting, example prompts, the mini-wire lens picker labels, attach/web-search button labels and titles, the prompt placeholder, the AI-response panel chrome, the deadline/questions lens-result UI text (register buttons, "no results" states, evidence/weakness labels), and every `alert()`/thrown-error message reachable from that tab (`workspace.errors.*`, all ICU-interpolated with `{fileName}`/`{error}`/etc. — ICU interpolation is required wherever the original template literal embedded a dynamic value, not just static copy). Two constants that back this tab changed shape to support localization: `IDLE_CONSOLE_MESSAGE` became `IDLE_CONSOLE_SENTINEL` (an opaque `'__idle__'` marker used only for equality checks — the actual displayed string is looked up via `t('workspace.idleMessage')` at render time, since a translated string can't itself be a stable comparison sentinel across locale switches), and `EXAMPLE_PROMPTS`/`CHAT_LENS_CHOICES` (`{icon, prompt}` / `{id, label}`) became `EXAMPLE_PROMPT_DEFS`/`CHAT_LENS_CHOICE_DEFS` (`{icon, key}` / `{id, key}`), resolving `key` to display text via `t()` in the render, not at module scope. Deadlines/professors/monitoring/logs tabs, and `lib/blocks/defaults.ts`'s `NODE_REGISTRY` labels (shared with the circuit board across both the chat mini-wire and the professor detail graph), remain untranslated — pick those up in the same tab-by-tab pattern rather than trying to do the whole file in one pass.

### Paid tier prep (`is_pro`)

No payment provider is wired up yet — `profiles.is_pro` (boolean, default `false`) is flipped manually in the Supabase dashboard, and everything downstream just reacts to that flag. [lib/plan-limits.ts](lib/plan-limits.ts) is the single source of truth for both tiers' numbers (`FREE_LIMITS`/`PRO_LIMITS`: `filesPerMonth`, `chatsPerMonth`, `maxProfessors`, `maxDocumentsPerProfessor`) via `getPlanLimits(isPro)` — change limits there, not at each call site. `pro_requests` (`user_id`, `email`, `memo`, `created_at`, own-rows-only RLS) is where the "Pro로 업그레이드하기" form (in `app/page.tsx`, opened by `openUpgradeModal()`) writes to; there's no automated follow-up, someone has to read this table and manually flip `is_pro` (and presumably email the person back) until real billing exists. Migration: [supabase/migrations/20260801_add_is_pro_and_pro_requests.sql](supabase/migrations/20260801_add_is_pro_and_pro_requests.sql) (idempotent — safe to run whether or not [20260701_create_logs_profiles_prompts_and_rls.sql](supabase/migrations/20260701_create_logs_profiles_prompts_and_rls.sql) has already been applied, since both create the same `profiles` SELECT policy under the same name).

Enforcement is split across two different mechanisms depending on where the underlying write happens:
- **Chat and file-processing monthly quotas are enforced server-side**, because both already go through a Next.js API route: `/api/chat` counts the caller's `logs` rows since `getMonthStartISOString()` (UTC month boundary — this is prep, not billing-grade, so no KST precision here) and `/api/extract` counts `document_uploads` rows over the same window, each comparing against `getPlanLimits(isPro)` after querying the caller's own `profiles.is_pro` (via `lib/auth/session.ts`'s `getSessionSupabase()`, added alongside the pre-existing `getSessionUserId()` for routes that need to actually query tables, not just identify the caller). On a hit, the route returns `{ error, limitReached: true, limitType: 'chat' | 'file' }` at `403` — the distinct `limitReached` flag is what tells the client to open the upgrade modal instead of rendering a plain error string. The file-quota query logic itself lives in `lib/plan-limits.ts`'s `checkFileQuota(supabase, userId)`, shared by two callers: `/api/extract` (text-file attachments, from both chat and the "교수님" tab) and `/api/upload-quota` (a `GET`, read-only, writes-nothing route) — the latter exists because chat image attachments skip `/api/extract` entirely and go straight to the vision API as base64, so `app/page.tsx`'s `handleChatAttachmentFiles` calls `/api/upload-quota` right before resizing/attaching an image to close that gap. If that quota-check call itself fails (network error, not an actual limit hit), it fails open — the attach proceeds rather than a secondary check taking down a primary feature.
- **Professor-count and per-professor-document-count limits are enforced client-side only**, in `app/page.tsx`'s `handleCreateProfessor`/`handleUploadProfessorFiles`, because those insert directly into `professors`/`documents` via RLS-scoped Supabase calls from the browser — there's no Next.js route in that path to check server-side without adding one purely for this. A modified client could bypass these two specific limits; that's an accepted gap for this prep pass, not a claim of real enforcement. (The pre-existing `MAX_PROFESSOR_DOCUMENTS` cost-safety cap in both `app/page.tsx` and `/api/analyze-professor/route.ts` is unrelated and unaffected — that one exists to bound re-analysis token cost regardless of tier, applies to both free and Pro, and is checked *after* the free-tier business limit since it's numerically looser.)

Hitting any of the four limits never just blocks silently — it calls `openUpgradeModal(message)`, which opens a centered, `max-h-[90vh] overflow-y-auto` overlay (the first real modal in this app; every other list/detail UI here deliberately avoids overlays, so this one earned specifically because a fixed badge needs somewhere to open into) pre-filled with `message` as both the shown context line and the default request-memo text (editable). Submitting posts to `pro_requests` and swaps the modal to a "곧 연락드릴게요" confirmation state. The same modal opens from a small always-visible "Pro"/"PRO" badge next to the logo (desktop sidebar header) and next to the hamburger button (mobile top bar) — clicking it directly always opens the same form with no context message, regardless of current `is_pro` status.

[app/privacy/page.tsx](app/privacy/page.tsx) is a public (no-login-required — added to `middleware.ts`'s `isPublicRoute` alongside `/login`/`/auth/*`) static English page stating what's collected (email, uploaded file content, conversation history), why (service provision, AI analysis), who it's shared with (OpenAI, Supabase), and retention (until account deletion, except free-tier conversation history at `FREE_LOG_RETENTION_DAYS = 30` days). It's deliberately plain English text, not routed through next-intl — a legal page isn't meant to flip with the UI locale toggle. [app/layout.tsx](app/layout.tsx) has a small global `<footer>` linking to it (below `{children}`, so it's reachable by scrolling past the full-height app shell, not pinned in view) — this is the first footer in the app; `app/login/page.tsx` has its own separate, unrelated `© {year}` line that this doesn't touch.

The 30-day free-tier retention line in that page is a real, enforced claim, not just copy: [app/api/cron/cleanup-logs/route.ts](app/api/cron/cleanup-logs/route.ts) is a Vercel Cron job ([vercel.json](vercel.json), daily at `0 3 * * *` UTC) that deletes any non-Pro user's `logs` rows older than `FREE_LOG_RETENTION_DAYS` (`lib/plan-limits.ts` — the same constant the privacy copy is written to match; if you ever change one, change both). It authenticates purely via `CRON_SECRET` (`Authorization: Bearer` header, which Vercel attaches automatically for configured crons — `middleware.ts` excludes `/api/cron/*` from the session-cookie gate for exactly this reason, since a cron invocation has no user session to check) and uses `SUPABASE_SERVICE_ROLE_KEY` to bypass RLS, because unlike every other route in this app it isn't acting on behalf of one authenticated caller — it has to reach across every free-tier user's rows in one pass. See "Env vars" above for the other (also justified) holder of this key.

[app/pricing/page.tsx](app/pricing/page.tsx) is the other public, plain-English, non-next-intl page (same reasoning as `/privacy`) — a two-column Free/Pro comparison that reads its numbers straight from `lib/plan-limits.ts` (`FREE_LIMITS`, `PRO_LIMITS`, `PRO_PRICE_LABEL`, `FREE_LOG_RETENTION_DAYS`) rather than hardcoding them, so it can't silently drift from the limits actually enforced. `PRO_PRICE_LABEL` (`"$4.99/month"`, derived from `PRO_PRICE_USD`) is also what every limit-reached surface shows now — the upgrade modal's heading, and the `error` string returned by the chat/file quota checks and the professor-count/document-count client-side checks — specifically because an earlier version of the upgrade prompt never stated the price, and people would hit a limit, see no price, and leave rather than convert. If the price ever changes, `PRO_PRICE_USD` is the only place to edit; everywhere else re-derives from it. A small "Pricing" link sits in the app sidebar (bottom, below the MCP-connection status badge) and in the global footer (`app/layout.tsx`, alongside the Privacy Policy link) — sidebar because logged-in users browsing the app should be able to find it, footer because it's reachable from every page including `/login`/`/privacy`/`/pricing` itself.
