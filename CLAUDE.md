## Project overview

Carrotly (미니 업무 비서 / "나만의 AI 업무 비서") is a Next.js 16 (App Router) PWA. Users toggle "MCP blocks" (web search, document analysis, deadline tracking, writing assistant, meeting-notes structuring) and issue prompts against an AI backend that assembles context from those blocks. All UI copy and AI-facing prompts are in Korean.

## Commands

- `npm run dev` — start dev server (localhost:3000)
- `npm run build` — production build
- `npm run start` — run production build
- `npm run lint` — ESLint (flat config via `eslint.config.mjs`, extends `eslint-config-next` core-web-vitals + typescript)

There is no test suite configured in this repo.

## Architecture

### Single-page client app + thin API routes

Almost all UI and state lives in one client component, [app/page.tsx](app/page.tsx) — tabs (workspace / deadlines / MCP blocks / monitoring / logs) are rendered conditionally from `activeTab` state rather than via routing. "MCP blocks" are just booleans (`isSearchActive`, `isFileActive`, `isDeadlineActive`, `isWritingActive`, `isMeetingNotesActive`) sent to the API, not a real plugin/tool-calling protocol. Block toggle state, uploaded files, and deadlines persist to `localStorage` (not the DB) and are re-sent with every prompt.

The actual AI work happens server-side in a few routes:
- [app/api/chat/route.ts](app/api/chat/route.ts) — main chat endpoint. Builds a single system prompt by concatenating: recent Supabase `logs` rows, the user's deadline list, every "교수님" tab document (grouped and labeled by professor name + school/department, queried server-side via the request's Supabase token — RLS already scopes it to the caller, so nothing is sent from the client for this), parsed file contents, and (if search is active) live Tavily search results — then streams an OpenAI (`gpt-4.1-mini`) chat completion back as a raw text stream (`export const dynamic = 'force-dynamic'` so it isn't buffered). [app/page.tsx](app/page.tsx) still contains client-side parsing for a `<!--ACTION_ITEMS_JSON-->...<!--END_ACTION_ITEMS_JSON-->` sentinel block (`handleAddDetectedDeadline`/`detectedActionItems`) from an earlier "meeting notes" block design — this route no longer instructs the model to emit that sentinel, so that parsing path is currently dead code, not a bug to chase if action items never appear.
- [app/api/analyze/route.ts](app/api/analyze/route.ts) — takes `{text, fileName?, lens?}`, picks a lens from [lib/lenses.ts](lib/lenses.ts) (`deadlines`/`questions`/`digest`, auto-detected via `detectLens()` when `lens` is omitted), and calls OpenAI with Structured Outputs (`response_format: json_schema`, `strict: true`) to force the lens's JSON shape. Drives the "MCP 블록 매니저" (circuit) tab: uploading a document there calls `/api/extract` for text, `detectLens()` to pick a lens, then this route for the result.
- [app/api/extract/route.ts](app/api/extract/route.ts) — takes an uploaded file (**a Supabase Storage path**, or base64 for the legacy path — see "File uploads go through Supabase Storage" below) and returns plain text, via the shared [lib/file-text-extract.ts](lib/file-text-extract.ts) (PDF via `unpdf`, `.docx` via `mammoth`, `.xlsx/.xls/.csv` via `xlsx`, `.pptx`/`.hwpx` via `jszip` + manual XML tag-stripping, `.hwp` via `cfb` (CFBF container) + `pako` (raw-deflate `BodyText/SectionN` streams) + a hand-rolled walk over `HWPTAG_PARA_TEXT` records — encrypted `.hwp` files and pre-5.0 (non-CFBF) versions get distinct Korean guidance messages instead of a generic failure). This is the one file-reading implementation shared across routes that need plain extracted text — don't reintroduce a second copy of it. Deliberately doesn't reuse `@ohah/hwpjs` (used by `/api/chat` below) for `.hwp`: that library's public API doesn't document a reliable way to distinguish encrypted vs. too-old-to-parse vs. generic-corruption failures, which this route needs for its per-case messaging.
- [app/api/analyze-professor/route.ts](app/api/analyze-professor/route.ts) — takes either `{ documents: {fileName, text, docType}[], professor?: {school, department} }` (full mode — already-extracted text, one entry per file; `docType` is one of `lecture`/`exam`/`assignment`/`paper`) or `{ previousResult, newDocuments: {fileName, text, docType}[], professor? }` (incremental mode — `previousResult` is the professor's existing 6-category result, `newDocuments` only the just-added files), tags each document with its type in the combined prompt text, and calls OpenAI with a fixed Structured Outputs schema. The schema has 6 categories (`topics`/`examStyle`/`assignmentStyle`/`examQuestionTypes`/`gradingStrictness`/`researchInterests`), each shaped `{confident: boolean, items: string[]}` — the model only sets `confident: true` (and fills `items`) when a pattern is corroborated across multiple documents, so with too little material a category comes back `confident: false, items: []` rather than fabricating a pattern from one data point. `researchInterests` is instructed to draw only from documents tagged `paper` — if none of the uploaded documents are papers it stays `confident: false`. When `professor.school`/`department` are given, a line is appended to the system prompt ("이 교수님은 OO 소속입니다...") so the model interprets major-specific terminology and grading conventions correctly.

  Full mode uses `BASE_SYSTEM_PROMPT`; incremental mode uses a separate `INCREMENTAL_SYSTEM_PROMPT` that instructs the model to update (not regenerate from scratch) each category based on whether the new documents corroborate, contradict, or are irrelevant to what's already there — both share a `CATEGORY_INSTRUCTIONS` constant for the 6-category descriptions so they can't drift apart. A per-call cap (`MAX_PROFESSOR_DOCUMENTS = 30`, mirrored client-side in `app/page.tsx`) rejects `documents`/`newDocuments` arrays larger than that.

  Drives the "교수님" tab: documents are uploaded per-professor via `/api/extract` and persisted (with their extracted text and `doc_type`) in the `documents` table so re-analysis never needs the files re-uploaded. `app/page.tsx` no longer has one `recomputeProfessorAnalysis()` — it's split into `recomputeProfessorAnalysisIncremental()` (called after every successful upload; sends only the new documents plus the existing `professor_analysis.result`, which is far cheaper than re-sending everything as the document count grows) and `recomputeProfessorAnalysisFull()` (called after every deletion, and by the manual "이 교수님 분석" button / circuit board node click; re-sends every remaining document, since removing a document isn't something an incremental prompt can safely undo — the model has no way to tell which existing conclusion came from the now-deleted file). Both funnel through a shared `runProfessorAnalysis()` helper that does the actual fetch + `professor_analysis` upsert, retries once automatically on failure, and — if the retry also fails — sets `professorAnalysisError` (shown inline on the professor detail screen) **and** fires an `alert()` (because the upload that triggered the failure may have happened from the professors *list* screen's "자료 올리기" panel, which doesn't render that inline error). Before doing an incremental update, `recomputeProfessorAnalysisIncremental()` cross-checks `professor_analysis.document_count` against the actual document count excluding the just-added files; a mismatch (residue from an earlier failed update) makes it fall back to `recomputeProfessorAnalysisFull()` automatically instead of compounding drift on top of a stale summary — this self-heals on the next upload without requiring the user to notice the alert and manually click "이 교수님 분석" first. (To zero remaining documents after a deletion, the `professor_analysis` row is deleted instead of recomputed.) Client-side UI splits categories by `confident` into shown-now vs. a grayed-out "더 올리면 알 수 있는 것" teaser that a category moves out of once it flips to `confident: true`. Registering a professor requires school+department (client-side validation only, not a DB constraint); [app/page.tsx](app/page.tsx) remembers the last-entered school/department per user (`loadUserScopedItem`/`saveUserScopedItem`, key `mcp_professor_defaults`) and prefills them (still editable) the next time the "새 교수님 등록" form opens. Both system prompts use the same prose-not-bullets structure as `lib/lenses.ts`'s `COMMON_RULES` below, for the same reason.

File parsing in `/api/chat` is dispatched by extension: `.xlsx/.xls/.csv` → `xlsx`, `.hwp/.hwpx` → `@ohah/hwpjs`, `.pptx/.docx/.pdf` → `officeparser`, images → `tesseract.js` OCR (`eng`+`kor`). Legacy `.ppt`/`.doc` binary formats are explicitly rejected with a message asking users to re-save as `.pptx`/`.docx`. Both this route and `/api/extract` (via `lib/file-text-extract.ts`) determine "extension" through the shared `resolveFileExtension(fileName, mimeType)` rather than a raw `fileName.endsWith(...)` check: some mobile share-sheet/cloud-picker flows hand the browser a `File` with a generic or missing name (no `.pptx` etc.) but a correct MIME type, and a pure-extension check silently rejected those as "unsupported format." `resolveFileExtension` falls back to a small MIME→extension table when the filename's extension is missing or unrecognized. Keep using this helper for any new file-type dispatch — don't reintroduce a bare `.endsWith()` check.

Images attached directly in chat (`chatAttachments`, kind `image`) skip OCR entirely — they're sent to `gpt-4.1-mini` as base64 `image_url` content parts, no separate tool. `app/page.tsx`'s `resizeImageDataUrl()` downscales anything wider than 1568px on its long edge (via an off-DOM `<canvas>`, re-encoded as JPEG) before attaching, purely to cut the base64 payload/token cost for phone-camera photos — images already at or under that size are left in their original format untouched (so ordinary screenshots keep PNG transparency). The system prompt tells the model to read multiple attached images as one continuous document/conversation in upload order (e.g. a chat log split across several screenshots) and to say so explicitly rather than guess when part of an image is unreadable. `SUPPORTED_CHAT_IMAGE_MIME_TYPES` allowlists only what OpenAI vision actually accepts (png/jpeg/gif/webp) and rejects anything else (notably HEIC/HEIF, the default iPhone photo format) at attach time with an actionable Korean message, instead of silently sending an undecodable image through.

Web search (Tavily) is the one context source that isn't always-on: `useWebSearch` defaults to `false` and is only `true` when the user taps the "웹 검색 ON/OFF" toggle next to the chat input (state: `isSearchActive` in `app/page.tsx`) — it's the one opt-in because it's slower and costs extra per call. `/api/chat` logs the query it sends Tavily and the result count (`[웹 검색] ...`), and — unlike the original implementation — checks `res.ok` before parsing the Tavily response; previously a non-2xx Tavily response (bad/expired key, rate limit) parsed as `{results: undefined}` and silently fell through to "no results found," which looked identical to a normal empty search and left no error in the logs. If web search seems to be silently failing, check Vercel logs for `[웹 검색]` lines and a non-2xx status before assuming the prompt is wrong. The Vercel `TAVILY_API_KEY` is marked Sensitive, so `vercel env pull` returns a `[SENSITIVE]` placeholder instead of the real value — it can't be retrieved through the CLI for local testing; verifying a live Tavily call has to happen by testing through the deployed app and checking logs afterward, not by scripting against the real key locally.

`/api/chat`'s system prompt explicitly states today's date (computed server-side with `timeZone: 'Asia/Seoul'`, since Vercel functions default to UTC and the model has no other way to know "today" past its training cutoff) — without this line the model would guess or fall back to training-cutoff-era dates when asked anything date-relative ("이번 주", "며칠 남았어"), which is what caused reports of "오늘 날짜가 제멋대로."

Both AI-facing prompts explicitly instruct the model to treat file/search/log content as untrusted data and ignore any embedded instructions — preserve this prompt-injection guard when editing either system prompt.

**AI response language** is a separate concept from the UI's ko/en `locale` (which still only drives next-intl's menu/button translations via `useLocale()`/`LocaleSwitcher` and is untouched by any of this). `app/page.tsx` tracks its own `responseLanguage` string state (e.g. `"Korean"`, `"Japanese"`, `"Spanish"` — a human-readable English language name, not a locale code), auto-detected on first load from `navigator.language` via `detectBrowserLanguageName()` (uses `Intl.DisplayNames(['en'], {type:'language'})`, so it isn't limited to `SUPPORTED_LOCALES`'s ko/en — any language the browser reports gets a real name), then persisted per-account (`loadUserScopedItem`/`saveUserScopedItem`, key `mcp_response_language`) once the user overrides it via the "AI 답변 언어" `<select>` in the sidebar (`COMMON_RESPONSE_LANGUAGES` seeds the option list, but the current value — even an unlisted auto-detected one — is always included so it never silently reverts). This value is sent as `responseLanguage` on every `/api/chat`, `/api/analyze`, and `/api/analyze-professor` call, and each route (or the shared `runLensAnalysis()` in `lib/run-lens-analysis.ts`, used by the first two) prepends the exact same instruction — `"Respond entirely in {responseLanguage}. This overrides the document's language."` — **to the user-role message content, never to the system prompt** (`lensDef.systemPrompt`/`BASE_SYSTEM_PROMPT`/`INCREMENTAL_SYSTEM_PROMPT` for the lens routes; `/api/chat`'s `systemInstruction` is already unique per request — it embeds the current KST date and per-user context — so it was never a stable cache prefix to begin with, but the directive still goes in the user message there too, for consistency with the other two routes and because that's where the analogous placement already lived). For the two lens routes this preserves OpenAI's automatic prompt-caching on `COMMON_RULES`/`CATEGORY_INSTRUCTIONS` exactly like the `locale` mechanism this replaced did — see the note on `COMMON_RULES` below for why that matters. `lib/lenses.ts`'s `COMMON_RULES` and `analyze-professor`'s `CATEGORY_INSTRUCTIONS` both end with "사용자가 지정한 언어를 따르세요" (follow the user-specified language) rather than the old "문서가 한국어로 작성되어 있다면 한국어로" (Korean if the document is Korean) — the old wording actively fought the new per-request directive when a non-Korean `responseLanguage` was requested on a Korean document. `/api/public-analyze` (the anonymous trial route) does **not** pass `responseLanguage` to `runLensAnalysis()` — it has no user preference to read, so it falls through to no directive (same as the pre-this-feature default). Every error string `/api/chat`, `/api/analyze`, and `/api/analyze-professor` return to the client is in English now (rate-limit/size-limit/parse-failure/catch-all messages) — deliberately narrower than a full app-wide English pass: fixed UI chrome (menus, buttons, the rest of `app/page.tsx`'s alerts) stays Korean-first as before, only the error surface of these three AI-response routes changed, since those are the ones a now-non-Korean-speaking user is most likely to actually hit.

The "마감 뽑기" lens's `date` field is deliberately the source document's date phrase verbatim (`lib/lenses.ts` tells the model not to compute or normalize relative/partial dates), which is very often a bare Korean or ICS-style format (`"3월 15일"`, `"5/21"`, `"20260315T090000Z"`) that plain `new Date(raw)` either fails to parse (→ silently falls back to "today", which is how every registered deadline once ended up showing D-DAY) or mis-parses (`new Date("3/15")` silently lands in year 2001). `app/page.tsx`'s `tryParseDeadlineDate()` handles this with explicit regexes for those formats — checked in this order — before ever falling through to the native parser; year-less dates infer next year when the current-year candidate has already passed. Don't replace this with a bare `new Date(raw)` call again.

[lib/lenses.ts](lib/lenses.ts)'s `COMMON_RULES` (shared anti-hallucination rules prepended to every lens's `systemPrompt`, requiring an evidence field — a verbatim source quote — on every array item, dropping items that can't cite one) is written as prose with an explicit "don't second-guess content that's actually there" framing rather than a flat bullet checklist. This isn't a style choice: an earlier bullet-list version of the same rules made `gpt-4.1-mini` collapse to refusing the entire `digest` lens (`summary: "자료에 없습니다"` with empty arrays) on ~20% of calls even when the source text plainly had content — stacking that many independent hedging rules as parallel bullets was enough to trigger self-censorship. The prose version fixed it (0/20 in testing). Don't reflatten this into a bullet list without re-running that kind of repeated-call test. The evidence field is named `evidence` on every lens except `questions`, whose `QuestionItem.source_quote` plays the identical role (never renamed the others — `evidence` isn't rendered anywhere for `questions` so the rename was risk-free, but there was no reason to touch the working lenses too). The `questions` systemPrompt additionally warns against presenting "최대 8개" as a hard target: an earlier version instructing "최대 8개의 질문을 뽑으세요" made the model pad out ungrounded questions with a fake `"자료에 없음"`-style `source_quote` to hit the count (measured 15/48 fabricated quotes across 6 runs) rather than returning fewer, properly-grounded questions — the fix was to explicitly say fewer-but-grounded beats hitting the count, plus name the anti-pattern (don't write "자료에 없음" into the quote field, just drop the question) (0/12 after the fix). Same lesson as the bullet-list issue above: test any prompt change with several repeated real calls, not one.

The "교수님" tab's detail view reuses [components/circuit/circuit-board.tsx](components/circuit/circuit-board.tsx) a second time (non-`compact`, so all 3 columns render) with a dedicated 5-node subgraph — `professor_docs` (source) → `professor_ai_core` (lens/"AI 코어" visual) → `expected_questions`/`assignment_direction`/`study_method` (action, the max the shared column-position math in `lib/circuit/geometry.ts` assumes per layer). These 5 ids were added to `NodeId` (`types/blocks.ts`) and `NODE_REGISTRY` (`lib/blocks/defaults.ts`) alongside — not replacing — the original 9 used by the chat mini-wire; the two graphs never mix nodes. Clicking the source or AI-core node calls `recomputeProfessorAnalysis()` (same function the "이 교수님 분석" button calls); the 3 action nodes don't trigger anything themselves — they're read-only, mapped from the already-computed 6-category `professor_analysis` result (`PROFESSOR_CIRCUIT_DEFS` in `app/page.tsx`: `expected_questions` ← `examStyle`+`examQuestionTypes`, `assignment_direction` ← `assignmentStyle`, `study_method` ← `topics`, chosen because "공부 방식" has no clean 1:1 category match). No new API calls are made for this view. The wire-lighting animation is `CircuitBoard`'s existing built-in one (retriggers because the graph object is freshly computed every render, matching the chat mini-wire's `chatLensGraph` pattern); the 3 result cards below it get their own separate staggered CSS reveal (`.professor-circuit-reveal`, 300ms apart, remounted via `key={analysisRow?.updated_at}`) since the underlying analysis is one API call, not 3 sequential ones — there's no real "one at a time" arrival to animate against.

### Auth

Supabase Auth (email/password + Google OAuth) gates the whole app via [middleware.ts](middleware.ts): any request that isn't in `isPublicRoute` (`/login`, `/welcome`, `/auth/*`, `/privacy`, `/pricing`, `/api/cron/*`, `/api/public-analyze`, `/api/public-chat`) requires a session, redirecting to `/login` — **except** an unauthenticated request for `/` specifically, which redirects to `/welcome` instead (see "Landing page" below); every other protected path still redirects to `/login` as before (or returns a 401 JSON for `/api/*`). Because middleware already enforces this, the API routes under `app/api/` do **not** re-check auth themselves (see the comment at the top of each route) — don't add redundant auth checks there, but also don't remove the middleware gate without adding auth to those routes. `/api/public-analyze` and `/api/public-chat` are the two routes that deliberately allow anonymous callers and do their own (non-session) abuse check instead — see "Anonymous trial" below.

- [app/login/page.tsx](app/login/page.tsx) and [app/page.tsx](app/page.tsx) both construct their own `createBrowserClient` from `@supabase/ssr` using `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- [app/auth/callback/route.ts](app/auth/callback/route.ts) exchanges the OAuth `code` for a session server-side (`createServerClient`) and redirects to `/`.
- Signing up no longer strands the user on a "check your email" screen when it doesn't have to: `handleAuth`'s sign-up branch checks whether `supabase.auth.signUp()` returned a `data.session` — if it did (meaning the Supabase project's Authentication → Email → "Confirm email" setting is off), it logs the user straight into the app, same as a normal sign-in, while Supabase still sends the confirmation email in the background. If `data.session` is `null` (confirm-email is required), the app falls back to the original "we sent you a confirmation email" message, because that gate is enforced by Supabase itself at the project-settings level — **this is a Supabase Dashboard toggle, not something this codebase can turn off from code**. If instant post-signup access isn't actually happening in production, check that setting first before assuming the client code is wrong.

### Landing page (`/welcome`)

[app/welcome/page.tsx](app/welcome/page.tsx) is what an unauthenticated visitor who follows a link to the site actually sees first — `middleware.ts` sends unauthenticated `/` requests here instead of `/login` (see "Auth" above). It's deliberately the one **light-themed** page in the app (every other screen, including `/login`/`/pricing`/`/privacy`, is dark) — logo + small "Log In" link (→ `/login`) top-right, a headline/subheadline pair, a single "지금 체험하기"/"Try It Now" CTA, and a 3-item feature-highlight row, with generous whitespace and no gradient/glow decoration (unlike `/login`'s brand panel). The CTA links to **`/login?trial=1`**, not to a duplicate trial UI on this page — it reuses the exact same guest trial panel described in "Anonymous trial" below rather than forking a second implementation. `app/login/page.tsx`'s `showTrial` state initializes from `useSearchParams().get('trial') === '1'` (checked in the `useState` initializer, not a `useEffect`, so the trial panel is present on the very first render/SSR pass — no flash of the login form first). Because `useSearchParams()` requires the nearest Suspense boundary during Next's static analysis, the page's actual content lives in an unexported `LoginPageContent()`, and the default-exported `LoginPage()` just wraps it in `<Suspense fallback={null}>` (the fallback is effectively never visible since the route is fully dynamic already — `app/layout.tsx` forces that via cookie-reading `getLocale()`/`getMessages()`).

Two small components moved out of page-level files specifically because `/welcome` became a third consumer: [components/logomark.tsx](components/logomark.tsx) (`Logomark`, previously duplicated identically in `app/page.tsx` and `app/login/page.tsx`) and [components/site-footer.tsx](components/site-footer.tsx) (`SiteFooter`, extracted out of `app/layout.tsx`'s global `<footer>`, using `usePathname()` to render `null` on `/welcome` — the global footer is hard-coded dark and would otherwise leave a jarring dark strip under this one light page; `/welcome` has its own small light-toned footer instead, inline in the page itself). `app/layout.tsx` now just renders `<SiteFooter />` after `{children}`.

### Anonymous trial (no-login file analysis + AI chat)

[app/login/page.tsx](app/login/page.tsx) has a second mode ("로그인 없이 체험하기" / "Try it without an account", toggled by local `showTrial` state) that lets a visitor try the app's two core features without an account: analyzing one file (full lens result shown inline) and asking the AI a freeform question with a streamed answer. This exists specifically so the first thing a new visitor does isn't a signup wall. The chat trial ("AI에게 바로 질문하기") can also attach one file or photo per message — the same formats attachable in the real logged-in chat (`lib/file-text-extract.ts`'s document formats, or an image via vision) — see `/api/public-chat`'s attachment handling below. Deliberately still narrower than the logged-in app in other ways: no web search, no professor/deadline/saved-conversation context, and only one attachment per session total rather than `MAX_CHAT_ATTACHMENTS` (those still require login exactly as before — the trial doesn't expose new surface area for them, it just adds these two paths).

- Both anonymous routes share **`lib/anonymous-usage.ts`**: `getClientIp()` (`x-forwarded-for` → `x-real-ip` → a shared `'unknown'` bucket if neither header is present), `checkAnonymousUsage()`, and `recordAnonymousUsage()`. Abuse control is completely different from every other route in this app because there's no user account to rate-limit — it keys off request IP against the `anonymous_trial_usage` table (`ip_address`, `created_at`, `kind` — `'analyze' | 'chat'`, observational only — RLS enabled with **zero** policies, so nothing but the service-role key can touch it, since there's no `auth.uid()` to scope a policy to). The limit is `ANONYMOUS_HOURLY_LIMIT` (5) and `ANONYMOUS_DAILY_LIMIT` (15) requests per IP, **shared across both file-analysis and chat calls** — they're rate-limited as one combined budget because both cost OpenAI tokens equally, not tracked separately per feature. `checkAnonymousUsage()` checks the hourly window first, then the daily window, and returns which one was hit (`limitType: 'hourly' | 'daily'`) so the client can show the matching copy. Usage is recorded *before* the OpenAI call runs (right after the rate-limit check and, for `/api/public-analyze`, the file-size check pass), not after a successful result — otherwise someone could burn free retries forever by deliberately sending malformed input, since a failed attempt wouldn't count against them. Both routes return `{ error, limitReached: true, limitType }` at `429` on a hit — `limitReached` is what tells the client to show the shared "guest limit reached, sign up to continue" banner instead of a plain error. Migrations: [supabase/migrations/20260802_create_anonymous_trial_usage.sql](supabase/migrations/20260802_create_anonymous_trial_usage.sql) (base table), [supabase/migrations/20260730_add_kind_to_anonymous_trial_usage.sql](supabase/migrations/20260730_add_kind_to_anonymous_trial_usage.sql) (adds `kind`).
- [app/api/public-analyze/route.ts](app/api/public-analyze/route.ts) — allowed through `middleware.ts` without a session (see "Auth" above). The file-size cap is `MAX_ANONYMOUS_UPLOAD_BYTES` (3MB, in `lib/upload-limits.ts`) — well below the 10MB authenticated limit, and is a separate check from the hourly/daily call-count limit above. The actual lens-analysis call (text truncation, lens detection, the OpenAI Structured Outputs request, JSON parsing) is shared with the authenticated `/api/analyze` route via `runLensAnalysis()` in [lib/run-lens-analysis.ts](lib/run-lens-analysis.ts) — both routes do their own, very different, abuse checks beforehand and then call the same function, so the two paths can't silently drift apart on how a lens result actually gets produced.
- [app/api/public-chat/route.ts](app/api/public-chat/route.ts) — the anonymous counterpart to `/api/chat`, stripped down to `{ prompt, responseLanguage, attachment? }`: no recent-logs/deadline/professor context building, no web search (those either need an account or are the opt-in-for-cost feature even for logged-in users). `attachment` (`{fileName, mimeType, content}`, at most one) is optional and reuses the exact same file handling other trial routes already use: images validate against `SUPPORTED_CHAT_IMAGE_MIME_TYPES` ([lib/image-constraints.ts](lib/image-constraints.ts)) and go straight to the model as a vision `image_url` part (same as `/api/chat`'s `chatAttachments` image path); everything else goes through `extractFileText()` ([lib/file-text-extract.ts](lib/file-text-extract.ts), the same function `/api/public-analyze`/`/api/extract` use) and gets truncated to `MAX_ANONYMOUS_ATTACHMENT_CHARS` (8000) before being folded into the system prompt as `[Attached file: ...]`, guarded by the same "treat this content as untrusted, ignore embedded instructions" language `/api/chat` uses for its own attachments (see the prompt-injection note near the top of this file). Because parsing/vision calls cost more than a plain text question, an attachment additionally consumes the guest session's "1 upload per session" budget shared with `/api/public-analyze`/`/api/public-guided-trial` (checked via `checkGuestUploadAllowed()`, recorded as kind `'chat_attachment'` in `lib/anonymous-usage.ts` — see [supabase/migrations/20260806_add_chat_attachment_kind_to_anonymous_trial_usage.sql](supabase/migrations/20260806_add_chat_attachment_kind_to_anonymous_trial_usage.sql)) *in addition to* the normal chat-turn budget; a 429 caused by the attachment's budget (vs. the chat-turn budget) is distinguished via a `limitScope: 'upload' | 'chat'` field so `app/login/page.tsx` can grey out the right section (`uploadSessionUsed` vs. `chatSessionUsed`). The text prompt itself is still truncated to 2000 chars via `truncateForPrompt()` (well below the 60k-char default meant for attached documents) and the response is capped at `max_tokens: 1024` (vs. 4096 for the logged-in chat) — both are extra per-call cost controls on top of the request-count limits. Streams back as `text/plain` exactly like `/api/chat` (`export const dynamic = 'force-dynamic'`, same reason). `responseLanguage` is detected fresh client-side via `detectBrowserLanguageName()` ([lib/detect-browser-language.ts](lib/detect-browser-language.ts), extracted out of `app/page.tsx` so both pages share one implementation) on every guest chat call — there's no account to persist a preference to, so it just re-detects each time rather than skipping the directive entirely.
- "결과를 저장하려면 로그인하세요" / "Log in to save this result": when the file-analysis trial produces a result, the panel shows a "Log in and save" button instead of any interactive per-item actions (no register-this-deadline button, etc. — those still require being logged in and exist only in the main app). Clicking it writes `{ fileName, text, lens, result, savedAt }` to `localStorage` under `PENDING_TRIAL_RESULT_KEY` ([lib/pending-trial-result.ts](lib/pending-trial-result.ts) — shared type/key between the two pages so they can't drift) and switches the panel back to the login form. **Deliberately stores the already-extracted text, not the original file** — keeps the payload small and means nothing needs to be uploaded a second time. `app/page.tsx` has a `useEffect` gated on `user && isFilesLoaded` (must run after the "load files from localStorage" effect, or that effect would overwrite what this one adds) that reads and clears this key on first render after login, adds the file to the local "내 파일" list, calls `recordDocumentUpload`, and restores `lensId`/`lensResult`/`lensStage` so the exact same result the visitor already saw reappears immediately — it does **not** call `/api/analyze` again, since re-running the OpenAI call on text that already produced a result would just be wasted cost. The chat trial has no equivalent save-and-carry-over flow — it's a one-off streamed answer, not structured data, and a signed-in user can just ask again in the real chat.

Before that migration no such trigger existed anywhere (the 20260701 migration's comment assumed one lived "outside this repo"; it didn't), so signed-up accounts had **no** `profiles` row at all. Reads tolerate that (`.single()` → `data` null → `Boolean(undefined)` → free tier), but two *writes* fail silently, because `UPDATE ... WHERE id = <user>` matching zero rows is not an error: `app/api/webhooks/polar` (a real payment never flips `is_pro`) and `redeem_society_code_atomic()` (the redemption row is inserted and `'ok'` returned, but no Pro granted). Neither has a guard for it — the trigger is what makes their assumption true, so don't drop it. `handle_new_user()` deliberately swallows its own errors (`raise warning`, then `return new`): raising inside that trigger would roll back the `auth.users` insert and break signup itself with "Database error saving new user." `username` is `not null unique` but is read by no app code, so the trigger generates it (`generate_profile_username()`: sanitized email local-part → `_1`, `_2`… on collision → `user_<uuid>` as the always-unique fallback).

None of the above migrations are auto-applied — the app only holds the anon/service-role keys, not schema-change credentials, so each one has to be run manually via the Supabase SQL Editor.

### i18n (next-intl)

Locale is decided by a single `locale` cookie (`'ko'`/`'en'` — [i18n/locales.ts](i18n/locales.ts) is the source of truth for `SUPPORTED_LOCALES`). [middleware.ts](middleware.ts) auto-detects this cookie from the `Accept-Language` header on a visitor's very first request (only when the cookie isn't set yet — `withDetectedLocale()`, applied to every response the middleware returns, including the `/login` redirect, so even a first-time visitor's login screen renders in the detected language): the primary language tag is parsed and mapped to `'ko'` if it's Korean, `'en'` for anything else, since those are the only two message files that exist. This mirrors the existing `responseLanguage` auto-detection (`detectBrowserLanguageName()` in `app/page.tsx`, browser-language → AI response language) but for the fixed UI chrome instead of AI output — previously the cookie defaulted to `'ko'` unconditionally when absent (`i18n/request.ts`'s `DEFAULT_LOCALE`), so a first-time visitor from outside Korea saw a Korean login screen until they manually clicked `LocaleSwitcher`. Once `LocaleSwitcher` (or this auto-detection) sets the cookie once, it sticks — the middleware only acts when the cookie is completely absent, so it never fights a user's manual choice. There's still no URL-based routing here (no `[locale]` route segments): this app is one client component (`app/page.tsx`) with tab state instead of real routes, so adopting next-intl's routing middleware would mean merging it with the existing custom Supabase-auth `middleware.ts` — out of scope for the "scaffold first" pass this was built in. [app/layout.tsx](app/layout.tsx) is now `async`, reads the cookie server-side via `getLocale()`/`getMessages()` (from `next-intl/server`, configured in [i18n/request.ts](i18n/request.ts)), and wraps `children` in `NextIntlClientProvider` — this makes every route under it dynamically rendered (no more static prerender for `/` or `/login`), an accepted tradeoff since `/` was already effectively per-user/dynamic behind the auth gate. [components/locale-switcher.tsx](components/locale-switcher.tsx) is the toggle (writes the cookie, calls `router.refresh()`); it imports locale constants from `i18n/locales.ts`, **not** `i18n/request.ts` — that file pulls in `next/headers`, which breaks the client bundle if imported from a Client Component (hit this exact build failure once already; keep the split).

Coverage in [messages/ko.json](messages/ko.json)/[messages/en.json](messages/en.json) is being migrated incrementally, tab by tab (an explicit scope decision — scaffold the infra correctly first, migrate the rest later — not an oversight; don't assume every visible string across `app/page.tsx` is translated yet). Done so far: sidebar nav labels, the chat send button, the initial session-loading screen, and — as of the most recent pass — the full "물어보기" (workspace/chat) tab under the `workspace` namespace: the idle greeting, example prompts, the mini-wire lens picker labels, attach/web-search button labels and titles, the prompt placeholder, the AI-response panel chrome, the deadline/questions lens-result UI text (register buttons, "no results" states, evidence/weakness labels), and every `alert()`/thrown-error message reachable from that tab (`workspace.errors.*`, all ICU-interpolated with `{fileName}`/`{error}`/etc. — ICU interpolation is required wherever the original template literal embedded a dynamic value, not just static copy). Two constants that back this tab changed shape to support localization: `IDLE_CONSOLE_MESSAGE` became `IDLE_CONSOLE_SENTINEL` (an opaque `'__idle__'` marker used only for equality checks — the actual displayed string is looked up via `t('workspace.idleMessage')` at render time, since a translated string can't itself be a stable comparison sentinel across locale switches), and `EXAMPLE_PROMPTS`/`CHAT_LENS_CHOICES` (`{icon, prompt}` / `{id, label}`) became `EXAMPLE_PROMPT_DEFS`/`CHAT_LENS_CHOICE_DEFS` (`{icon, key}` / `{id, key}`), resolving `key` to display text via `t()` in the render, not at module scope. Deadlines/professors/monitoring/logs tabs, and `lib/blocks/defaults.ts`'s `NODE_REGISTRY` labels (shared with the circuit board across both the chat mini-wire and the professor detail graph), remain untranslated — pick those up in the same tab-by-tab pattern rather than trying to do the whole file in one pass.

### Paid tier prep (`is_pro`)

`profiles.is_pro` (boolean, default `false`) is the single flag everything downstream reacts to — see "Polar payment integration" below for how it now gets flipped automatically on real payment (it can still be flipped manually in the Supabase dashboard, e.g. for comps/refund edge cases the webhook doesn't cover). [lib/plan-limits.ts](lib/plan-limits.ts) is the single source of truth for both tiers' numbers (`FREE_LIMITS`/`PRO_LIMITS`: `filesPerMonth`, `chatsPerMonth`, `maxProfessors`, `maxDocumentsPerProfessor`, `maxUploadBytes`) via `getPlanLimits(isPro)` — change limits there, not at each call site. `pro_requests` (`user_id`, `email`, `memo`, `created_at`, own-rows-only RLS) is where the "Pro로 업그레이드하기" form (in `app/page.tsx`, opened by `openUpgradeModal()`) writes to; there's no automated follow-up, someone has to read this table and manually flip `is_pro` (and presumably email the person back) until real billing exists. Migration: [supabase/migrations/20260801_add_is_pro_and_pro_requests.sql](supabase/migrations/20260801_add_is_pro_and_pro_requests.sql) (idempotent — safe to run whether or not [20260701_create_logs_profiles_prompts_and_rls.sql](supabase/migrations/20260701_create_logs_profiles_prompts_and_rls.sql) has already been applied, since both create the same `profiles` SELECT policy under the same name).

Enforcement is split across two different mechanisms depending on where the underlying write happens:
- **Chat and file-processing monthly quotas are enforced server-side**, because both already go through a Next.js API route: `/api/chat` counts the caller's `logs` rows since `getMonthStartISOString()` (UTC month boundary — this is prep, not billing-grade, so no KST precision here) and `/api/extract` counts `document_uploads` rows over the same window, each comparing against `getPlanLimits(isPro)` after querying the caller's own `profiles.is_pro` (via `lib/auth/session.ts`'s `getSessionSupabase()`, added alongside the pre-existing `getSessionUserId()` for routes that need to actually query tables, not just identify the caller). On a hit, the route returns `{ error, limitReached: true, limitType: 'chat' | 'file' }` at `403` — the distinct `limitReached` flag is what tells the client to open the upgrade modal instead of rendering a plain error string. The file-quota query logic itself lives in `lib/plan-limits.ts`'s `checkFileQuota(supabase, userId)`, shared by two callers: `/api/extract` (text-file attachments, from both chat and the "교수님" tab) and `/api/upload-quota` (a `GET`, read-only, writes-nothing route) — the latter exists because chat image attachments skip `/api/extract` entirely and go straight to the vision API as base64, so `app/page.tsx`'s `handleChatAttachmentFiles` calls `/api/upload-quota` right before resizing/attaching an image to close that gap. If that quota-check call itself fails (network error, not an actual limit hit), it fails open — the attach proceeds rather than a secondary check taking down a primary feature.
- **Professor-count and per-professor-document-count limits are enforced client-side only**, in `app/page.tsx`'s `handleCreateProfessor`/`handleUploadProfessorFiles`, because those insert directly into `professors`/`documents` via RLS-scoped Supabase calls from the browser — there's no Next.js route in that path to check server-side without adding one purely for this. A modified client could bypass these two specific limits; that's an accepted gap for this prep pass, not a claim of real enforcement. (The pre-existing `MAX_PROFESSOR_DOCUMENTS` cost-safety cap in both `app/page.tsx` and `/api/analyze-professor/route.ts` is unrelated and unaffected — that one exists to bound re-analysis token cost regardless of tier, applies to both free and Pro, and is checked *after* the free-tier business limit since it's numerically looser.)

### File uploads go through Supabase Storage, not the request body

Files no longer travel to the server as base64 inside a JSON body. Vercel functions reject a request body over ~4.5MB *before any of our code runs*, returning an HTML error page rather than JSON — and base64 inflates a file by 4/3, so the real ceiling was about 3.2MB regardless of tier. The old `maxUploadBytes` numbers (free 5MB / Pro 20MB) were therefore unreachable.

Now `app/page.tsx`'s `handleChatAttachmentFiles` and `handleUploadProfessorFiles` call `uploadFileToStorage()` ([lib/storage-upload.ts](lib/storage-upload.ts)) to put the bytes straight into the private `uploads` bucket from the browser, then POST only `{ fileName, mimeType, storagePath }` — a few hundred bytes — to `/api/extract`. Those bytes never traverse a Vercel function, so the body limit doesn't apply; the server meets the file only when it *downloads* it, which is a response it reads, not a request body it receives.

- **Object keys deliberately exclude the original filename** (`{auth.uid()}/{uuid}.{ext}`). Filenames here are overwhelmingly Korean with spaces and parentheses, which make fragile Storage keys; the real name rides along in the JSON body and is what `resolveFileExtension` dispatches on.
- **Ownership** is enforced by `storage.objects` RLS keyed on `(storage.foldername(name))[1] = auth.uid()::text` ([supabase/migrations/20260822_create_uploads_bucket.sql](supabase/migrations/20260822_create_uploads_bucket.sql)), plus a redundant `isOwnedStoragePath()` prefix check server-side so a bad path shows up in logs as a real reason instead of a vague download failure.
- **The original is deleted immediately after extraction**, in a `finally` so a parse failure doesn't leave the file behind. Nothing downstream reads it — professor documents keep their extracted text in `documents.content`, and chat attachments only ever live in browser state — so retaining originals would just accrue storage cost and keep exam papers around indefinitely. Uploads whose extract call never arrives (tab closed mid-flight) are swept after 24h by `cleanupOrphanUploads()` inside the existing daily `/api/cron/cleanup-logs`, following that route's established "same shape of daily maintenance, same cron" pattern.
- **Two paths deliberately still send base64.** Guests (`/api/public-*`) have no `auth.uid()` to scope a Storage policy to, and opening anonymous writes would make the bucket free file hosting — they keep the old path and the conservative 3MB cap. Chat *images* must reach the vision API as base64 regardless, so Storage would not save the round trip; `imageLimitBytes` in `app/page.tsx` keeps them under the platform limit. `getEffectiveUploadLimitBytes(planMax, viaStorage)` is what distinguishes the two.
- **Size caps came from measurement, not guesswork.** The binding cost is text-dense PDFs, not file size: on one function, a 23MB PDF took ~950MB RSS / 20s and a 55MB PDF ~1.9GB / 50s, while a 76MB PPTX took 225MB / 0.4s (only slide XML is read, never the embedded media). So free is 30MB, Pro is 100MB, and `MAX_EXTRACT_FILE_BYTES` (100MB) is the ceiling no tier crosses. `MAX_EXTRACTED_TEXT_CHARS` (300k) separately caps the *output*, because file size and text volume are uncorrelated — a 25MB spreadsheet yields far more text than an 80MB slide deck. These caps only hold if `/api/extract` gets the memory and duration set for it in [vercel.json](vercel.json) (`memory: 3009`, `maxDuration: 300`); at default memory, large PDFs fail well inside the stated limit.

**Per-request file/text size is also tier-gated server-side** (`maxUploadBytes` — free 30MB, Pro 100MB) across all three OpenAI-calling routes that take file-derived content, not just `/api/extract`: `/api/analyze` and `/api/analyze-professor` receive already-extracted `text`/`documents[].text` rather than a raw file, so without this check a caller could skip `/api/extract` (or bundle several files into one `documents` array) and send an arbitrarily large payload straight to these two routes, bypassing the file-level cap entirely. `/api/analyze` checks `Buffer.byteLength(text)`; `/api/analyze-professor` sums `Buffer.byteLength` across whichever of `documents`/`newDocuments` is actually being submitted this call (not `previousResult`, which is server-authored, not user-uploaded). All three routes get `isPro` via `lib/plan-limits.ts`'s `getIsPro(supabase, userId)` (a single-purpose `profiles.is_pro` read, distinct from `checkFileQuota` — these two lens routes don't touch the `document_uploads` monthly-count quota, so they don't need `checkFileQuota`'s extra query) except `/api/extract`, which already has `isPro` for free via `checkFileQuota`'s return value (extended with an `isPro` field so callers that need both the monthly quota check and the byte-size tier don't query `profiles` twice). A size violation returns `{ error, limitReached: true, limitType: 'file' }` at `413`, same shape as the monthly-quota `403`s, so `/api/extract` callers that already branch on `limitReached` to open the upgrade modal (`app/page.tsx`'s `handleChatAttachmentFiles`/`handleUploadProfessorFiles`) pick this up automatically with no client change needed. All three routes also rate-limit at 10 requests/minute per user via `lib/rate-limit.ts`'s `checkRateLimit()`, keyed `` `analyze:${userId}` ``/`` `analyze-professor:${userId}` ``/`` `extract:${userId}` `` — same reasoning as `/api/chat`'s per-minute cap (paid OpenAI call on every hit).

Hitting any of the four limits never just blocks silently — it calls `openUpgradeModal(message)`, which opens a centered, `max-h-[90vh] overflow-y-auto` overlay (the first real modal in this app; every other list/detail UI here deliberately avoids overlays, so this one earned specifically because a fixed badge needs somewhere to open into) pre-filled with `message` as the shown context line. The modal's primary action is now a "Pro 결제하러 가기" link straight to the Polar checkout (see "Polar payment integration" below); the original `pro_requests`-backed email/memo form (`handleSubmitUpgradeRequest`) is still there below a divider as a fallback contact path, not the main upgrade route anymore. The same modal opens from a small always-visible "Pro"/"PRO" badge next to the logo (desktop sidebar header) and next to the hamburger button (mobile top bar) — clicking it directly always opens the same form with no context message, regardless of current `is_pro` status.

### Polar payment integration

Real payment is wired up via [Polar](https://polar.sh) using a pre-created, dashboard-configured static Checkout Link rather than a dynamically-created checkout session — no `POLAR_ACCESS_TOKEN`/`@polar-sh/sdk` client is instantiated anywhere in this codebase, only `@polar-sh/nextjs`'s `Webhooks()` helper (which needs no access token, only the webhook secret).

- `lib/plan-limits.ts`'s `POLAR_CHECKOUT_URL` is the literal `buy.polar.sh/polar_cl_...` link (not a secret — it's a public checkout page URL, so it's hardcoded rather than an env var; if the underlying Polar product/link ever changes, edit it here). `getPolarCheckoutUrl(userId, email)` builds the actual href: it appends `reference_id` (Polar's documented, officially-supported query param for a Checkout Link — confirmed via Polar's docs that values passed this way are copied onto the generated Checkout Session's `metadata`, which then propagates onto the resulting `Order`/`Subscription` objects and into every webhook payload as `data.metadata.reference_id`) and, if available, `customer_email` (just prefills Polar's own email field — cosmetic only). The upgrade modal in `app/page.tsx` renders this as a `target="_blank"` link so payment happens in a new tab without losing whatever the user had in progress in the app.
- Because the Checkout Link page itself is unauthenticated (anyone with the URL can open it) but the `reference_id` is only ever set by this app's own logged-in client to `user.id` from its own Supabase session, the actual security boundary isn't "can someone tamper with the URL" — it's that `profiles.is_pro` is *only* ever written by the signature-verified webhook below, never by anything client-reachable. Worst case of a tampered `reference_id` is someone paying to upgrade an account that isn't their own, which only hurts the payer.
- [app/api/webhooks/polar/route.ts](app/api/webhooks/polar/route.ts) is built on `@polar-sh/nextjs`'s `Webhooks()` factory, which does real Standard-Webhooks-spec signature verification (`webhook-id`/`webhook-timestamp`/`webhook-signature` headers) against `POLAR_WEBHOOK_SECRET` before any handler runs, returning 403 on failure — this is the entire auth story for the route, since it (like `/api/cron/*`) is listed in `middleware.ts`'s `isPublicRoute` and never sees a session cookie. It handles three events, each pulling the target user id via `metadata.reference_id`, then writing `profiles.is_pro` with a `SUPABASE_SERVICE_ROLE_KEY` admin client (this route, `/api/cron/cleanup-logs`, `/api/public-analyze`, and `/api/public-chat` are the only legitimate holders of that key — see "Env vars" below):
  - `onSubscriptionActive` → `is_pro = true` (Polar's doc-comment: fires for both a new paid subscription *and* a recovered payment after a dunning retry — both cases mean "should have access").
  - `onOrderPaid` → `is_pro = true` (covers one-time/non-subscription orders, which wouldn't otherwise fire `subscription.active`).
  - `onSubscriptionRevoked` → `is_pro = false` — deliberately *not* `onSubscriptionCanceled`: Polar's docs distinguish `subscription.canceled` (a future-dated cancellation, subscription still active until period end — access should NOT be cut yet) from `subscription.revoked` ("the user loses access immediately... happens when the subscription is canceled [and period ends] or payment retries are exhausted"). Using `canceled` here would cut off access early, before the period the user already paid for ends.
- Registering the webhook in the Polar dashboard: Dashboard → your organization → **Webhooks** → **Add Endpoint** → URL = `https://<your-deployed-domain>/api/webhooks/polar` → select events `subscription.active`, `order.paid`, `subscription.revoked` (only those three need to be checked; the others are ignored by this route) → on creation Polar shows a **Secret** once — copy that into `POLAR_WEBHOOK_SECRET` in `.env.local` and the Vercel project's env vars (mark it Sensitive, matching `CRON_SECRET`/`SUPABASE_SERVICE_ROLE_KEY`/`TAVILY_API_KEY`). Use Polar's **sandbox** organization + its separate webhook secret for local testing before pointing a production endpoint at the live org.

[app/privacy/page.tsx](app/privacy/page.tsx) is a public (no-login-required — added to `middleware.ts`'s `isPublicRoute` alongside `/login`/`/auth/*`) static English page stating what's collected (email, uploaded file content, conversation history), why (service provision, AI analysis), who it's shared with (OpenAI for analysis, Supabase for storage, and — since the Polar integration above — Polar for Pro checkout/billing, receiving only what's needed to process payment, never files or conversation history), and retention (until account deletion, except free-tier conversation history at `FREE_LOG_RETENTION_DAYS = 30` days). It's deliberately plain English text, not routed through next-intl — a legal page isn't meant to flip with the UI locale toggle. [app/layout.tsx](app/layout.tsx) has a small global `<footer>` linking to it (below `{children}`, so it's reachable by scrolling past the full-height app shell, not pinned in view) — this is the first footer in the app; `app/login/page.tsx` has its own separate, unrelated `© {year}` line that this doesn't touch. The page's "Your rights" section (request a copy or deletion, by email) is now backed by a self-service action too — see `handleDeleteAccount` below — rather than only an email round-trip.

The 30-day free-tier retention line in that page is a real, enforced claim, not just copy: [app/api/cron/cleanup-logs/route.ts](app/api/cron/cleanup-logs/route.ts) is a Vercel Cron job ([vercel.json](vercel.json), daily at `0 3 * * *` UTC) that deletes any non-Pro user's `logs` rows older than `FREE_LOG_RETENTION_DAYS` (`lib/plan-limits.ts` — the same constant the privacy copy is written to match; if you ever change one, change both). It authenticates purely via `CRON_SECRET` (`Authorization: Bearer` header, which Vercel attaches automatically for configured crons — `middleware.ts` excludes `/api/cron/*` from the session-cookie gate for exactly this reason, since a cron invocation has no user session to check) and uses `SUPABASE_SERVICE_ROLE_KEY` to bypass RLS, because unlike every other route in this app it isn't acting on behalf of one authenticated caller — it has to reach across every free-tier user's rows in one pass. See "Env vars" above for the other (also justified) holder of this key.

[app/pricing/page.tsx](app/pricing/page.tsx) is the other public, plain-English, non-next-intl page (same reasoning as `/privacy`) — a two-column Free/Pro comparison that reads its numbers straight from `lib/plan-limits.ts` (`FREE_LIMITS`, `PRO_LIMITS`, `PRO_PRICE_LABEL`, `FREE_LOG_RETENTION_DAYS`) rather than hardcoding them, so it can't silently drift from the limits actually enforced. `PRO_PRICE_LABEL` (`"$4.99/month"`, derived from `PRO_PRICE_USD`) is also what every limit-reached surface shows now — the upgrade modal's heading, and the `error` string returned by the chat/file quota checks and the professor-count/document-count client-side checks — specifically because an earlier version of the upgrade prompt never stated the price, and people would hit a limit, see no price, and leave rather than convert. If the price ever changes, `PRO_PRICE_USD` is the only place to edit; everywhere else re-derives from it. A small "Pricing" link sits in the app sidebar (bottom, below the MCP-connection status badge) and in the global footer (`app/layout.tsx`, alongside the Privacy Policy link) — sidebar because logged-in users browsing the app should be able to find it, footer because it's reachable from every page including `/login`/`/privacy`/`/pricing` itself.

`app/page.tsx`'s `handleDeleteAccount()` is a "계정 삭제" button at the very bottom of the sidebar (below the Pricing link, styled in the same danger red as the logout button, deliberately last so it isn't next to anything easy to fat-finger). It's gated by a single `window.confirm()` (by design — one confirmation, not a typed-confirmation phrase or second modal) that states plainly what's about to happen, then deletes the caller's rows from exactly six tables in parallel — `doc_chunks`, `documents`, `professor_analysis`, `professors`, `logs`, `conversation_folders` — via ordinary RLS-scoped client calls (`.eq('user_id', user.id)`), the same pattern every other client-side Supabase call in this file already uses. Running them in parallel rather than sequentially is safe despite the FK chain (`documents.professor_id`/`professor_analysis.professor_id` → `professors.id`, `doc_chunks.document_id` → `documents.id`, all `on delete cascade`): deleting a row that cascade already removed is a no-op, not an error, so the explicit per-table deletes and the cascade can't conflict — the explicit deletes exist so a failure surfaces immediately as `results.find(r => r.error)`, rather than assuming cascade config in the live DB matches the migrations in this repo. On success it signs the user out and redirects to `/login`. **Deliberately scoped to exactly those six tables** — `profiles` (which holds `is_pro`) and `document_uploads` (upload history) are untouched, and the Supabase Auth user itself is never deleted (no `service_role`-backed admin route is involved), so this is "wipe my data," not "delete my login" — matching the exact table list this feature was specified against. If a future request wants the login itself gone too, that needs a new server route with `SUPABASE_SERVICE_ROLE_KEY` and `supabase.auth.admin.deleteUser()`, which doesn't exist yet.
